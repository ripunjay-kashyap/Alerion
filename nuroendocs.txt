NUROEN.AI PUBLIC DOCUMENTATION & API INTEGRATION RESEARCH
========================================================

Research date: 2026-10-03
Primary documentation reviewed: https://www.nuroen.com/docs
Purpose: Produce a comprehensive, implementation-focused summary of Nuroen's public documentation and investigate whether the public web explains how to invoke agents programmatically, start runs, or resolve human approvals through an API.

IMPORTANT SCOPE NOTE
--------------------
This is an original research summary, not a verbatim mirror of Nuroen's copyrighted documentation. It paraphrases the public materials and records a small number of short phrases where needed for verification.

The findings apply to PUBLICLY ACCESSIBLE material located during this research. They do not prove that Nuroen has no private, tenant-only, beta-only, sales-provided, or authenticated developer documentation.

BOTTOM LINE
-----------
The statement below is supported by Nuroen's current public documentation:

"Nuroen's public docs describe the platform but do not provide an implementable public API contract for calling it."

More specifically:

1. Nuroen publicly advertises programmatic access, including a "Governed SDK" and a "REST API" described as entitlement-verified integration endpoints.
2. The public "Platform APIs" documentation explicitly says it is an overview, not a REST catalog.
3. That same API page explicitly says it does not list REST paths, HTTP methods, or payloads.
4. The public docs describe graph CRUD, simulation, publishing/rollback, provenance export, runtime governance, execution, and approvals conceptually.
5. The public docs do not provide enough information to implement an external client that:
   - authenticates to the Nuroen API,
   - starts a production agent run,
   - supplies the run input in a documented request body,
   - polls/streams a run,
   - cancels a run,
   - lists pending approvals,
   - approves/rejects/modifies a pending action through a documented API call.
6. I did not locate a public OpenAPI/Swagger definition, official public Postman collection, official Nuroen SDK package with usage examples, or public endpoint reference during searches of Nuroen's site and broader indexed sources.
7. Public materials strongly suggest such internal/programmatic surfaces exist, but the public web does not publish the wire contract needed to use them safely.

The strongest direct evidence is Nuroen's own API reference wording:
- It calls the API material an "overview, not a REST catalog."
- It says the page "does not list REST paths, methods, or payloads."
- It describes conceptual YAML as "not a public API path."

Those statements make the documentation gap explicit rather than merely accidental.

1. WHAT NUROEN IS
-----------------
Nuroen describes itself as an enterprise agentic-AI platform for building, governing, deploying, operating, and scaling AI agents over real enterprise systems.

The public product model combines:
- a web platform / centralized control plane,
- a visual agent builder,
- governance and policy controls,
- operations and monitoring,
- skills and retrieval-augmented generation (RAG),
- connectors,
- a marketplace,
- an agentic IDE / Companion Mode,
- runtime enforcement,
- model routing,
- provenance / audit logging,
- enterprise identity and deployment controls.

The product is positioned around "governed autonomy": agents can reason and take actions, but execution is constrained by organizational policy, approvals, permissions, budgets, and auditability.

Nuroen's public docs repeatedly emphasize that governance is part of the execution path, rather than a UI-only configuration layer.

2. PUBLIC DOCUMENTATION STRUCTURE
---------------------------------
The main documentation page currently presents seven guides/reference areas grouped around:
- Quickstart
- First agent
- Agent catalog / marketplace
- Connect a system
- Governance at runtime
- Platform APIs
- Model routing

The documentation states that it covers the journey from the first agent through runtime policy, credits, and deployment.

2.1 Quickstart / entry into the product
---------------------------------------
The quickstart is product-oriented rather than API-oriented.

The documented path is:
- open "Get Started,"
- land on the Nuroen portal in explore mode,
- inspect the workspace,
- create/sign into an account when attempting to simulate, publish, or run,
- then choose a path such as catalog install, connector setup, first-agent build, or governance review.

The docs say the public marketing site is not the signed-in workspace and that execution happens in the portal.

This distinction matters for API research: the public docs tell the reader to use the product UI rather than giving a command-line or HTTP quickstart.

2.2 Building a first governed agent
-----------------------------------
The public build model is:

Define -> Confirm -> Validate -> Build

Define:
- A user describes the intended job in natural language.
- Nuroen produces a reviewable, governed specification.
- The specification can include outcome, skills, connectors, policy, and knowledge.

Confirm:
- The user accepts the scope, connected systems, autonomy envelope, and approval structure.

Validate:
- Nuroen checks for blockers before production.
- Examples include unauthenticated connectors, missing secrets, type mismatches, and approval gates with no assignee.

Build:
- The approved design becomes a governed graph/canvas.
- The user can then refine, simulate, and publish.

Nuroen explicitly says the conceptual specification shown in the documentation is not a public REST path.

The important technical model is that an agent is not described as a single prompt. It is represented as a schema-constrained, typed graph.

2.3 Agent graph / Agent IR
--------------------------
The docs describe a shared graph representation used by the web platform, IDE, and runtime.

Key characteristics:
- typed nodes,
- typed edges,
- immutable versions,
- publish/rollback lifecycle,
- production runs pin the version they execute,
- schema validation is required before deploy.

The public site also uses the term "Agent IR" for the schema-validated agent definition.

However, the public documentation does not publish the full Agent IR schema, JSON Schema URL, version identifier, or downloadable schema artifact needed to construct an agent graph outside the product.

2.4 Marketplace / catalog
-------------------------
The marketplace path is:

Browse -> Install -> Customize -> Deploy

The docs describe:
- prebuilt agents,
- skills,
- workflow templates,
- connectors,
- knowledge packs.

The docs currently cite 89 prebuilt agents across functions such as HR, IT, Finance, Manufacturing, and Marketing.

An install is described as cloning a starting graph into the user's workspace. It is not a direct publish or production bypass. The cloned graph still requires connector binding, validation, simulation, governance, and deployment.

Marketplace certification does not bypass the tenant's own policies.

2.5 Connectors and enterprise systems
-------------------------------------
The integration lifecycle is:

Discover -> Connect -> Bind -> Act

Discover:
- Find a prebuilt integration or use custom APIs / MCP-based capabilities.

Connect:
- Authenticate the target system.
- Public docs mention OAuth, API keys, and enterprise SSO as connector authentication methods.

Bind:
- Attach a credential reference to the graph.
- Secrets remain in the tenant runtime vault rather than on the visual canvas.

Act:
- The published agent uses scoped credentials under runtime policy.

The docs describe integrations for categories such as:
- databases,
- CRM,
- ITSM,
- cloud platforms,
- collaboration,
- MCP servers,
- custom APIs,
- ERP,
- warehouses,
- document stores,
- webhooks / event-driven triggers.

The docs say connectors use a shared SDK for auth, retry, checkpointing, and idempotency. However, they do not provide a public Connector SDK package name, installation command, API reference, or code sample.

2.6 Governance at runtime
-------------------------
The governance path is described as:

Policy -> Gate -> Supervise -> Prove

Nuroen documents an autonomy ladder from L0 through L4, with L2 (policy-gated) presented as the normal production default.

Every action is described as passing five important runtime gates:

1. Scope
   Checks whether the request is inside the allowed job/knowledge boundary. With Strict RAG, off-task or ungrounded work can be rejected before generation.

2. Confidence
   Scores the candidate against evidence/grounding. Low confidence can pause the run for review.

3. Policy
   Applies organizational rules such as autonomy, blast radius, residency, and other restrictions.

4. Approval
   High-impact or high-risk actions are routed to designated approvers. Pending actions are described as holding without partial side effects.

5. Budget
   Checks credit balance and task ceilings before model spend.

Only after these gates pass does the action execute.

2.7 Human approval model
------------------------
The public docs contain substantial conceptual detail about approvals:

- high-impact work can require a named approver,
- an approval gate with no assignee can block production,
- risky proposals enter a unified review queue,
- an approver can approve, reject/deny, or modify,
- policy may support a 24-hour undo window in some circumstances,
- approvals are written to the provenance ledger,
- approval behavior applies across chat, schedules, and orchestrated runs.

What the docs do NOT publish is the programmatic approval contract.

I found no public documentation that specifies:
- GET/list pending approvals endpoint,
- fetch approval details endpoint,
- POST approve endpoint,
- POST reject/deny endpoint,
- modify-and-approve payload,
- approval token format,
- approver identity binding,
- optimistic concurrency/version field,
- idempotency semantics,
- approval timeout API behavior,
- webhook callback for "approval required,"
- webhook callback for "approval resolved,"
- how a paused run resumes after external approval.

Therefore the public docs describe the approval capability but do not establish whether a third-party client can resolve approvals through a supported public API.

Important distinction:
This is NOT evidence that an approval API does not exist. It is evidence that the public documentation reviewed does not specify how to use one.

2.8 Provenance and audit
------------------------
The docs describe a tamper-evident, SHA-256 hash-chained provenance ledger.

The record can include:
- runtime gate outcomes,
- approvals and rejections,
- spend events,
- pinned graph version,
- execution outcome.

Enterprise materials say audit history can be exported to SIEM/GRC or archival systems and that custom retention is available in enterprise contexts.

Again, the public API page describes provenance export conceptually but does not provide a public export endpoint, method, schema, auth example, or pagination contract.

2.9 Model routing
-----------------
Nuroen describes model selection as policy-driven rather than a model dropdown chosen per call.

Inputs to routing include:
- capability,
- data residency,
- budget,
- policy / allowlists,
- BYOM preference.

The router is described as selecting the cheapest model that satisfies the required capability after policy/residency/budget constraints.

Builders can tune temperature per skill, but the public docs say this does not bypass residency, grounding, or budget policy.

Enterprise modes can support:
- shared SaaS,
- dedicated,
- bring-your-own-cloud,
- air-gapped/on-prem deployment,
- controlled egress,
- sovereign/local models.

3. WHAT THE PUBLIC SITE SAYS ABOUT REST API / SDK ACCESS
--------------------------------------------------------
The broader Nuroen site is more explicit than the docs about the existence of programmatic access.

The main public site advertises:
- "Governed SDK" -> policy-bound programmatic integration
- "REST API" -> entitlement-verified integration endpoints
- "Agent IR" -> schema-validated definitions at deploy

The enterprise/identity material also says authorization is enforced on every API route and that a user without permission cannot bypass build/publish/execute authorization simply by calling the API directly.

This is significant because it confirms that Nuroen intends API-level access to exist.

But it still does not tell an external developer how to call that API.

6. APPROVAL API: WHAT IS MISSING
--------------------------------
The approval feature is well described as a product/governance concept, but not as an external API workflow.

A complete programmatic approval flow would normally need documentation for at least:

1. Detecting approval required
   - run status value
   - approval ID
   - pending action snapshot
   - risk tier
   - reason/policy that triggered approval
   - expiry/deadline

2. Querying approvals
   - list pending approvals
   - filter by workspace/agent/run/assignee
   - retrieve one approval

3. Resolving approval
   - approve
   - reject/deny
   - modify proposal
   - comment/reason
   - delegation or reassignment

4. Authentication/authorization
   - who is allowed to approve
   - whether service accounts may approve
   - whether approval requires interactive user identity
   - separation-of-duties constraints

5. Resume behavior
   - whether resolution automatically resumes a run
   - whether the caller must invoke resume
   - how stale/expired approvals behave
   - what happens when policy changes while pending

6. Events
   - webhook/event when approval is created
   - webhook/event when approval is resolved
   - signature verification
   - retry behavior

7. Idempotency/audit
   - duplicate approval resolution behavior
   - conflict handling
   - immutable audit fields
   - modification versioning

None of these wire-level details were found in the public documentation reviewed.

8. IMPORTANT DOCUMENTATION INCONSISTENCIES / AMBIGUITIES
---------------------------------------------------------
A few public-source details deserve caution:

A. Connector counts
The main docs cite "200+" connectors/components in several places, while other marketing/FAQ material references "250+" enterprise integrations. Treat these as marketing/catalog counts that may be evolving rather than a stable API guarantee.

B. API existence versus API publication
The public site clearly claims a REST API and Governed SDK exist, while the public API documentation intentionally withholds the actual REST contract. The most reasonable reading is:
- API/programmatic access exists in the product,
- public marketing acknowledges it,
- public docs currently provide architecture/behavioral overviews,
- access to the concrete contract may be entitlement-, tenant-, beta-, or sales-controlled.

C. "External systems all hit the same gates"
The docs say studio, code, schedules, and external systems all pass the same governance gates. This indicates external invocation is part of the architecture, but it still does not disclose the invocation protocol.

D. "Execute by calling the API directly"
The enterprise identity copy says API authorization prevents unauthorized users from building, publishing, or executing by calling the API directly. This strongly implies execution routes exist. It does not reveal their path or payload.

10. WHAT AN INTEGRATOR CAN SAFELY ASSUME
----------------------------------------
Based on the public docs, it is reasonable to assume at a conceptual level that:

- Nuroen has a versioned agent graph / Agent IR.
- Agents can be created, updated, published, and rolled back.
- Simulation exists.
- Production runs exist.
- Runs pass scope, confidence, policy, approval, and budget gates.
- High-impact actions can pause awaiting approval.
- Nuroen maintains provenance/audit records.
- Programmatic/REST integration exists in some form.
- Authorization applies to API routes.
- External systems can participate in governed execution.
- Connectors can include webhooks, APIs, and MCP servers.

It is NOT safe to assume:
- any endpoint name,
- any hostname,
- any `/v1/...` convention,
- any Authorization header scheme,
- any JSON request shape,
- any run status enum,
- any approval endpoint,
- any webhook schema,
- any SDK package name,
- any undocumented internal browser endpoint is a supported public API.

Do not reverse-engineer or hard-code guessed production endpoints as a substitute for an official contract.

13. IMPLEMENTATION RECOMMENDATION UNTIL THE CONTRACT IS PROVIDED
---------------------------------------------------------------
Treat Nuroen as a product with documented capabilities but an unpublished public wire contract.

For production integration:
- use the supported portal/product workflow,
- request the official API/SDK contract from Nuroen,
- avoid guessed endpoints,
- avoid relying on browser-internal routes as stable APIs,
- require a documented auth model,
- require explicit run and approval state models,
- require idempotency and retry semantics before automating side-effecting actions,
- require approval identity and audit semantics before allowing machine-driven approval resolution.

If Nuroen supplies a tenant-only OpenAPI specification, that should become the source of truth over the current public overview.

FINAL CONCLUSION
----------------
As of 2026-10-03, Nuroen's public web documentation is architecture- and product-capability-oriented, not a complete developer API reference.

The public site indicates that REST API and SDK access exist, and the product clearly supports execution, governance, approvals, and audit. But the public docs intentionally omit the concrete protocol details required to integrate: endpoint paths, HTTP methods, authentication format, run request/response schemas, lifecycle APIs, and approval-resolution APIs.

Therefore, an external developer cannot responsibly implement a supported "start agent run -> wait for approval -> resolve approval -> resume -> collect result" integration using only the public documentation located in this research.

The next required artifact is Nuroen's official entitlement-specific API/SDK documentation or OpenAPI specification.
